# AetherGuard 智能服务器安全防御平台

## 产品介绍

> **版本：** v1.0<br>
> **日期：** 2026-07-15<br>
> **适用对象：** 企业安全负责人（CISO）、运维与 SRE、合规与审计、技术评审

---

## 一、一句话定位

> **AetherGuard 是一套"应用内驻留 + 外部硬件兜底"的服务器安全平台：分布式 Agent 在主机内部检测与响应，控制平面统一编排与审计，自研 Gateway Appliance 在服务器失陷后作为可审计、默认隔离的硬件最后防线。**

即使攻击者获取了服务器 root 权限，也无法不经外部硬件授权恢复关键网络连接。

---

## 二、我们解决什么问题

### 2.1 传统安全架构的致命盲区

当前企业普遍部署了 WAF、EDR、防火墙、IDS/IPS 等多层防御。但所有这些防御有一个**共同弱点**：

> **它们都运行在可被攻破的软件环境里。**

当攻击者通过 0-day 漏洞、供应链投毒或钓鱼攻击获取服务器 root 权限后，传统防御全部失效：

| 传统防御 | 被 root 后的命运 |
|---------|-----------------|
| EDR Agent | 被卸载、被静默、被伪造心跳 |
| 主机防火墙 | 规则被篡改，出站连接重新打开 |
| 日志系统 | 被清空、被伪造、被重定向 |
| WAF/IDS | 只能看流量，无法控制物理连通 |
| 自动化运维脚本 | 被劫持执行破坏性操作 |

**真实案例：**
- **Colonial Pipeline（2021）**：勒索软件攻陷 IT 网络后横向移动，最终被迫手动关闭 OT 侧，造成美国东海岸燃油供应中断 6 天。事后分析指出，缺乏**远程可控的物理隔离机制**是损失扩大的关键原因。
- **某三甲医院（2024）**：服务器被勒索软件加密后，运维人员紧急拔网线隔离，但无审计记录、无恢复流程，核心业务中断 72 小时，患者数据恢复耗时 3 周。

### 2.2 企业面临的五大核心痛点

| 痛点 | 现状 | 后果 |
|------|------|------|
| **静态规则失效** | WAF 依赖人工维护规则库，无法应对 AI 驱动的变形攻击 | 新型攻击绕过后无感知 |
| **失陷后无底线** | 一旦 root 失守，攻击者可自由横向移动、外传数据 | 平均检测时间（MTTD）> 200 天 |
| **应急响应混乱** | "拔网线"靠人工判断，无标准流程，无审计留痕 | 恢复时间不可控，合规审计无法通过 |
| **等保合规压力** | 等保 2.0 三级要求"重要网络区域间可靠技术隔离" | 传统软件隔离可被 root 绕过 |
| **高危操作无授权** | 主机移除、数据擦除、工厂复位等操作仅靠软件审批 | 内部威胁 + 外部攻击双重风险 |

## 三、AetherGuard 解决方案

### 3.1 两层防御架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        AetherGuard 安全架构                      │
├─────────────────────────────┬───────────────────────────────────┤
│      Layer 1: 主机检测层      │     Layer 2: 硬件最后防线          │
│      （软件信任边界内）        │     （软件信任边界外）              │
├─────────────────────────────┼───────────────────────────────────┤
│  • 分布式 Agent 实时检测      │  • Gateway Appliance 硬件网关      │
│  • 7 层 AI Agent 威胁分析     │  • STM32H5 独立安全控制器          │
│  • 漏洞扫描（Nuclei）         │  • OPTIGA Trust M 安全芯片         │
│  • 攻击模拟器（35+ 种）       │  • 物理继电器 + 反馈回路           │
│  • 规则 + AI 混合检测         │  • 默认隔离，硬件授权才释放         │
└─────────────────────────────┴───────────────────────────────────┘
                              │
                              ▼
                    ┌─────────────────────┐
                    │   控制平面（审计中心）  │
                    │  策略下发 · 审计归档   │
                    │  对象锁 · 链式校验     │
                    └─────────────────────┘
```

**核心设计思想：**

> **Layer 1 负责"尽量早发现、尽量早阻断"；Layer 2 负责"即使被攻破，还有最后一道物理防线"。**

AetherGuard 不替代 WAF、EDR 或防火墙，而是在它们**全部失效后**，提供一条**不可绕过的硬件控制边界**。

### 3.2 核心价值主张

| 价值维度 | 传统方案 | AetherGuard |
|---------|---------|-------------|
| **信任边界** | 被保护服务器内部 | 被保护服务器**外部** |
| **失陷后能力** | 无 | **远程物理隔离 + 授权恢复** |
| **高危操作授权** | 软件审批（可被篡改） | **硬件签名 + 物理确认** |
| **审计不可删除** | 本地日志（可被清空） | **对象锁链式归档** |
| **隔离可恢复性** | 拔网线（永久断网） | **自动到期回隔离** |

### 4.1 全局安全态势感知（Dashboard）

- 实时流量分析：请求量、拦截量、平均延迟、全局健康度

### 4.2 分布式 Agent 集群管理

- 批量节点管理：成百上千 Agent 统一管理
- 主机层防御：操作系统级检测，无需流量绕行
- 自动注册上线：部署后自动接入控制台
- 离线告警：心跳超时自动触发告警

### 4.3 7 层 AI Agent 检测管线

```
L1 协同层 ──► L2 角色层（红队/蓝队/分析师）
    │
    ▼
L3 场景遍历 ──► L4 能力实例化 ──► L5 辩论协议（多模型交叉验证）
    │
    ▼
L6 异构模型（本地 Ollama + 云端 DeepSeek/GPT-4）
    │
    ▼
L7 综合决策（案件归档 + 自演化）
```

- **硬约束**：正常流量 **0% 误报**
- 数据集评估：检测率 64%，正常流量 FPR 0%
- 支持隐私模式：敏感数据不出私有网络

### 4.4 Final Defense Mode（最终防线模式）

AetherGuard 的核心差异化功能。高危操作（主机移除、数据擦除、工厂复位、关键配置变更）必须满足：

1. **本地策略匹配**：Companion 读取已签名的本地策略文件
2. **硬件 Grant 签名**：Secure Element 使用 ECDSA P-256 签名
3. **Policy Digest 绑定**：跨 4 个服务逐字比对，任何不匹配即 fail-closed
4. **单调计数器防回滚**：3 套独立高水位，严格递增
5. **Challenge 去重**：16 槽环形窗口，防止重放攻击
6. **Interlock 反馈闭环**：物理继电器 + 辅助触点反馈
7. **对象锁审计归档**：每次授权决策不可篡改

### 4.5 AetherGuard Root-Resistant Gateway Appliance

#### 硬件四模块架构

| 模块 | 组件 | 职责 |
|------|------|------|
| **M1** | 工业多网口网关（Protectli VP2430） | 数据桥 + Gateway Daemon |
| **M2** | STM32H5 安全控制器（Cortex-M33, 250MHz） | 最终授权决策引擎 |
| **M3** | OPTIGA Trust M（CC EAL6+） | 非导出私钥 + ECDSA 签名 + 单调计数器 |
| **M4** | DIN-rail 继电器 + 反馈触点 + E-Stop | 物理通断 + 故障安全 |

#### 关键安全属性

- **默认隔离（Fail-Closed）**：上电即 isolated，SERVER↔LAN/WAN 无转发
- **自动恢复**：授权释放后，窗口到期自动回 isolated
- **急停锁存**：红色蘑菇头按钮按下即永久隔离，需人工复位
- **独立 MGMT 通道**：即使 isolated，Appliance 自身管理通道仍可用

### 4.6 主动漏洞扫描

- 基于 Nuclei 引擎：20,000+ 漏洞模板
- 20+ 安全基线检测：SSL 证书过期、敏感端口、HTTP 安全头
- CVE 漏洞扫描 + 配置缺陷检测
- 一键合规报告导出（等保 2.0 格式）

### 4.7 攻击模拟器

- 35+ 攻击类型：SQL 注入、XSS、路径遍历、命令注入、CSRF、SSRF、JWT 攻击
- 实时分析面板：AI 决策过程可视化
- 拦截率统计：每次模拟自动计算拦截率
- 历史记录对比：追踪防御能力变化趋势

## 六、典型应用场景

### 场景一：勒索软件应急响应（金融/医疗）

**问题：** 服务器被勒索软件感染，需要立即隔离防止横向移动，但传统"拔网线"操作：
- 需要人工到场或登录云控制台
- 断网后无法远程恢复，恢复流程混乱
- 无审计记录，合规审计无法通过

**AetherGuard 方案：**
1. Layer 1 Agent 检测到异常加密行为 → 自动告警
2. 安全团队通过 Dashboard 一键触发 **Final Defense 隔离**
3. Gateway Appliance 物理断开 SERVER↔LAN/WAN
4. 运维人员远程排查，确认安全后提交 **硬件授权释放请求**
5. M2 控制器验证 grant 签名 + policyDigest + counter + challenge
6. 验证通过 → 短暂释放网络窗口（如 5 分钟）→ 自动回 isolated
7. 全程审计：谁、何时、为何隔离/恢复，全部对象锁归档

**效果：** 隔离时间从小时级缩短到秒级，恢复可远程授权，审计一次性通过。

---

### 场景二：高危运维操作授权（云服务商 / SaaS）

**问题：** 运维人员需要对生产服务器执行数据擦除、主机移除、关键配置变更等操作。传统审批流程：
- 仅靠软件审批，审批记录可被 root 篡改
- 操作执行后无物理留痕
- 误操作或恶意内部人员可造成不可逆损失

**AetherGuard 方案：**
1. 运维人员在控制台提交高危操作请求
2. 控制平面生成 hardware context（含 policyDigest、challenge、breakerTarget）
3. 请求发送至 Gateway Appliance
4. M2 控制器要求**物理确认按钮**按下（可选）或**远程硬件授权**
5. Secure Element 使用私钥对 grant 签名
6. M2 验证全链 → 执行操作 + 记录审计

**效果：** 即使运维人员账号被盗、控制平面被攻陷，没有 Secure Element 的私钥签名，高危操作无法执行。

---

### 场景三：等保 2.0 / 关基合规（电力 / 政务 / 运营商）

**问题：** 等保 2.0 三级要求"重要网络区域与其他网络区域之间应采取可靠的技术隔离手段"。传统方案：
- 软件防火墙/VLAN 可被 root 绕过
- 缺乏物理隔离的审计证据
- 工控网与企业网隔离靠网闸，但网闸无 AI 检测能力

**AetherGuard 方案：**
1. Gateway Appliance 物理串接在关键服务器与 LAN/WAN 之间
2. 默认 isolated 状态 = **物理隔离证据**
3. AI 检测管线实时分析流量，0% FPR 硬约束
4. 审计归档支持等保 2.0 合规报告一键导出
5. Final Defense 的高危操作授权 = **不可篡改的管理证据**

**效果：** 直接满足等保 2.0 三级"物理隔离"加分项，关基保护条例"网络安全监测预警"要求。
